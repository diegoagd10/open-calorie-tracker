## Visual findings — corrected after screenshot review

1. **[P2] Long credential names expand delete controls into large multiline blocks.** The supported 80-character test name is deliberately made of Q characters. The application repeats that complete name in the visible delete-button label, creating a five-line button on mobile and a wide multiline button on desktop. These are test data, but the rendering is real. A compact visible Delete label with an account-specific accessible name and target confirmation would preserve identification without expanding the action control. Evidence: [mobile](long-name-mobile.png), [desktop](security-desktop.png). Source: `app/routes/settings.security.tsx`, credential-list button label.
2. **[P2] Credential rows do not maintain consistent alignment as names grow.** Default list indentation puts credential content farther right than the surrounding controls. Wrapping flex rows place short names and actions side by side, but an ordinary name such as Member recovery key moves its action below the name; the long-name row changes again to a full-width action. A stable row layout and explicit list spacing are needed for predictable mobile alignment. Evidence: [short names](six-keys-mobile.png), [ordinary name wrapping](final-key-confirmation-mobile.png), [long name](long-name-mobile.png). Source: `app/account.module.css` (`.keyRow`) and the unstyled `ul` in security settings.
3. **[P3] Destructive confirmation and cancellation have identical visual emphasis.** Delete, Confirm deletion, and Cancel deletion use the same green submit-button styling. The labels remain understandable and the keyboard flow works, but the visual hierarchy does not distinguish the destructive operation from cancellation. Evidence: [deletion confirmation](final-key-confirmation-mobile.png). Source: `app/routes/settings.security.tsx`, removal form controls.

The initial functional results below still stand. Zero axe violations and no horizontal overflow do not establish satisfactory visual quality. These findings were identified from the captured rendered UI and subsequently resolved in the linked follow-up review.

## Remaining acceptance work

1. Manually enroll and authenticate the owner's compatible YubiKey across intended USB/NFC/browser combinations and Proton Pass extension/mobile providers. Virtual authenticators establish protocol journeys, not physical-device or provider compatibility.
2. Repeat public HTTPS and non-loopback HTTP LAN checks on the actual deployment host/public hostname. This run used a local HTTPS preview and a real non-loopback LAN listener on the QA machine, not the deployed tunnel.
3. This browser run did not independently repeat the full protocol/race/rollback/rate-limit/security-event matrix, migration preservation, disabled-account/reactivation matrix, mandatory replacement after key authentication, all five enabled-mode deletions through the final key, or production-container command availability. It checked the individual deletion and final deletion seams on separate account journeys. The existing spec comment records prior deterministic/deep/container evidence; those suites were **not rerun** here.
4. Completed in follow-up: fixes and repeated screenshot review for long credential names, consistent credential-row alignment, and deletion/cancellation hierarchy.
5. Preserve the existing preview-only enrollment guard and leave the parent spec open until its release acceptance requirements are satisfied.
