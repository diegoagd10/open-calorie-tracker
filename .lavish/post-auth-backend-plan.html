01

Business meaning

Onboarding is the gate between identity and product use.

Authentication has already proved the email and created a device session. The product still cannot open the daily log because the account has not chosen US or metric display and has not supplied the eight daily values used for progress comparisons.

Current state

Authenticated, onboarding incomplete

The approved auth response says setupComplete: false and next: "/setup".

Target state

Authenticated, onboarding complete

One successful onboarding command returns setupComplete: true and next: "/log/today".

What “daily goals” means

These are the user's manually entered daily comparison values for calories, water, protein, carbohydrates, fat, fiber, sugar, and sodium. The product does not calculate or recommend them. Sugar and sodium act as maximums; the other six act as targets.

Requirement source: PRD §4 requires unit preference plus all eight values before entering the log. PRD §12 requires manual goals. TDD §6 already defines the setup gate on accounts.onboarding_completed_at.
02

Exact flow

One business action: complete account onboarding.

The existing auth session response already tells the client where to go. The onboarding screen submits once to a single new endpoint. Ongoing preference changes, goal maintenance, and the rest of the daily-log backend are deliberately outside this plan.

03

Protection and ownership

A session token proves identity; server context selects the account.

The approved __Host-session cookie contains an opaque random token. It is a bearer token carried by a cookie, but authorization is a server-side session because the API hashes it and looks up an active auth_sessions row. It is not a JWT and does not contain an account ID.

Step Enforcement Failure
1 · Authenticate Hash cookie token; match current or valid grace token on an unrevoked session. 401 UNAUTHENTICATED
2 · Derive owner Copy auth_sessions.account_id into trusted request context. Setup handler does not run.
3 · Reject client ownership The request schema has no accountId or email field. 422 VALIDATION_ERROR
4 · Write by owner Both inserts and the account update use only context.accountId. Foreign-key rollback.
5 · Protect cookie mutation Require same-origin JSON and validate Origin; cookie is Secure, HttpOnly, SameSite=Lax. 403 INVALID_ORIGIN
Proof, not convention: integration tests create two valid sessions, complete onboarding with session A, and verify only account A received preferences, goals, and onboarding_completed_at.
04

Endpoint and request

PUT /v1/account/onboarding

PUT fits because onboarding is one singleton state for the authenticated account and retries must be safe. No Idempotency-Key is required: an identical retry returns the saved result; a later request with different values returns 409 ONBOARDING_ALREADY_COMPLETED instead of silently editing ongoing settings.

05

SQLite tables

Two new tables extend the existing account.

The approved accounts table remains the ownership root and already contains onboarding_completed_at. Onboarding adds one unit preference row and one first daily-goal version. The separate goal table preserves the required future ability to change goals without rewriting history, but no maintenance API is designed now.

One-to-zero-or-one

Before onboarding an account has no preference row; afterward its primary-key foreign key allows exactly one.

One-to-zero-or-many

Onboarding creates the first goal version. Future goal changes may add versions for later effective dates.

No child-to-child FK

Preferences and goals join independently to the authenticated account; neither owns the other.

Table Business record Ownership Important constraint
account_preferences The account's selected US or metric display. account_id is both PK and FK. Exactly one preference row per account.
daily_goal_versions The eight daily comparison values beginning on one calendar date. FK to accounts.id. Unique account + effective date.

API units

Request names state units explicitly: kcal, mL, grams, and mg. The UI converts US display input before sending.

Storage units

SQLite stores kcal, mL, and nutrient milligrams as integers. This avoids floating-point drift while retaining decimal grams.

06

Build and test

A small vertical slice with a hard transaction boundary.

The first deliverable is not a repository unit test. It is an HTTP-to-SQLite vertical slice that begins with the approved authentication boundary: create a real active session, complete onboarding with its cookie, then call the existing session endpoint again to prove that the setup gate changed.

Start

A verified account and active session from the approved auth flow.

Exercise

PUT /v1/account/onboarding through real HTTP middleware and SQLite.

Prove

Session gate, response, preference row, goal row, and account isolation.

1

Migration

Add the two STRICT tables after the approved auth schema. Enable foreign keys on every connection.

2

Session middleware

Resolve the active session and expose only trusted accountId to the handler.

3

Onboarding transaction

Insert preference, insert first goal, and mark onboarding complete in one BEGIN IMMEDIATE transaction.

4

Supporting cases

Verify success, rollback, exact replay, changed replay, two-account isolation, revoked session, invalid origin, all field errors, and database contention.

Acceptance: a first-time authenticated user can submit the required onboarding once; either all values and the setup gate are committed, or none are; no request can configure another account.
Explicit stopping point: after returning next: "/log/today", this plan ends. The daily-log backend is a separate design exercise.
