01

Design Basis

The proposal implements confirmed behavior and resolves only the mechanics needed to make it safe and buildable. Food, goals, images, and synchronization remain outside this authentication boundary.

Requirement Source Design response
Valid email can create a private account PRD 19 Create the account only when a link is successfully exchanged.
Email verification is mandatory PRD 20 No account or session exists before possession of a one-time bearer token is proven.
Passwordless email link PRD 21 Opaque 256-bit link token; store only its SHA-256 digest.
Delivery failure and resend PRD 22–23 Return a stable request ID on failure; resend is explicit and retryable.
Persistent, multi-phone sessions PRD 24–25 One session row and cookie per phone; no global replacement on sign-in.
Current-phone sign-out only PRD 26–27 Revoke only the session identified by the presented cookie.
Setup before daily log PRD 32–45 Session response exposes setupComplete and the next route.
Replay protection and isolation TDD 219–221 Atomic token consumption; authenticated ownership derives only from the session.
02

Proposed Decisions

Identity

Verify first, create second

A request stores an email challenge, not an account. Exchange atomically creates or finds the account by canonical email.

Token

Single-use, newest-link-wins

Links expire after 15 minutes. A successful resend supersedes earlier active links only after the email provider accepts the new delivery.

Session

Independent opaque cookie

Each phone receives a different random credential in a __Host-session HttpOnly cookie. Signing out revokes one row.

Privacy

No account enumeration

Existing and new emails follow the same request path and response. Delivery errors describe provider availability, never account existence.

Delivery

Fragment-carried bearer

Email links use /auth/verify#token=…, keeping the bearer out of HTTP logs and preventing ordinary HTTP-only link scanners from consuming it.

Policy

Explicit revocation only

Per the recorded product decision, the server does not expire sessions for inactivity. A session remains valid until this phone signs out.

03

Sign-in Flow

Provider I/O stays outside SQLite transactions. The security-sensitive exchange is one short BEGIN IMMEDIATE transaction.

sequenceDiagram autonumber actor U as User participant C as PWA client participant A as Auth API participant D as SQLite participant E as Email provider U->>C: Enter email C->>A: POST /v1/auth/magic-links A->>D: Insert request + pending token A->>E: Send /auth/verify#token=… alt Provider accepts delivery E-->>A: Accepted A->>D: Activate new token and supersede previous A-->>C: 202 requestId + expiry else Provider rejects or is unavailable E-->>A: Failure A->>D: Mark delivery_failed A-->>C: 503 retryable + requestId end U->>C: Open emailed link Note over C: Fragment is never sent in HTTP request C->>A: POST /v1/auth/sessions { token } A->>D: BEGIN IMMEDIATE D-->>A: Consume token exactly once A->>D: Upsert account + insert device session A->>D: COMMIT A-->>C: 201 + __Host-session cookie C-->>U: Route to /setup or /log/today
Client route, not API: GET /auth/verify#token=<raw-token>. JavaScript reads the fragment, clears it with history.replaceState, then exchanges it.

Endpoint Proposal

All responses use JSON except cookie headers. The two send operations require a UUID Idempotency-Key so a lost mobile response cannot send duplicate mail.

05

SQLite Data Model

Only actual foreign-key relationships appear below. A consumed link resolves an account transactionally by email_key; it is intentionally not tied to an account before verification.

erDiagram accounts ||--o{ auth_sessions : "owns via account_id FK" auth_login_requests ||--|{ auth_magic_link_tokens : "issues via request_id FK" accounts { TEXT id PK TEXT email TEXT email_key UK INTEGER email_verified_at INTEGER onboarding_completed_at } auth_login_requests { TEXT id PK TEXT email TEXT email_key TEXT create_key UK INTEGER expires_at INTEGER last_delivery_at } auth_magic_link_tokens { TEXT id PK TEXT request_id FK BLOB token_hash UK TEXT delivery_key UK TEXT status INTEGER expires_at } auth_sessions { TEXT id PK TEXT account_id FK BLOB token_hash UK BLOB previous_token_hash INTEGER revoked_at } auth_rate_limit_buckets { TEXT scope PK BLOB key_hash PK INTEGER window_started_at PK INTEGER attempts }
Table One row represents Relationship Why it exists
accounts One verified identity; email_key UNIQUE prevents a second account for the same normalized email 1 account → 0..N intentionally separate phone sessions Owns identity and the setup-complete gate. Multiple sessions are required by PRD 25.
auth_sessions One signed-in browser or phone account_id FK → accounts Allows several phones and current-phone sign-out.
auth_login_requests One “email me a link” UI attempt 1 request → 1..N rows in auth_magic_link_tokens Groups the first email and every resend under one request ID, expiry, and cooldown.
auth_magic_link_tokens One secret link in the initial or a resend email request_id FK → login requests Tracks a distinct secret, provider result, expiry, consumption, and supersession.
auth_rate_limit_buckets One short-lived counter for an email or IP key No FK by design Stops email bombing, provider-cost abuse, and repeated token guesses. For example, request 6 for one email in 15 minutes returns 429.
Why no link-to-account foreign key? A first-time user has no account yet. Exchange follows token → request → email_key, then atomically creates or finds the account and inserts its session.
Multiple sessions are not prevented. They are the mechanism for PRD 25: each phone gets one auth_sessions row. The account stays singular because accounts.email_key is unique; auth_sessions.account_id is deliberately not unique.

Why email and email_key?

email is the trimmed display and delivery value. email_key is its Unicode-normalized, lowercased lookup value, for example Diego@Example.COM → diego@example.com. It enforces one account per email and powers non-plaintext rate keys. Do not rely on SQLite NOCASE, which is ASCII-limited by default.

How is onboarding_completed_at used?

Auth creates it as NULL. Both session endpoints return setupComplete: false and next: /setup until the setup transaction saves unit preferences plus the first goal version, then stamps this field. Non-null routes to /log/today.

Why a request separate from tokens?

One UI attempt can have several delivery attempts. This request row owns the email, UI expiry, and resend cooldown. Every initial send or resend gets a separate token row, so its secret and provider outcome can be consumed, failed, or superseded independently.

Why do rate buckets have no FK?

Throttling must run before authentication and before a first-time account exists. Each row is keyed by a scope plus an HMAC digest of the normalized email or IP prefix. It is an expiring security counter, not user-owned domain data. Keeping it in SQLite makes increments atomic and preserves limits across an API restart; a future multi-node deployment should replace it with a shared edge or Redis limiter.

06

Executable SQLite DDL

SQLite ≥ 3.37 · STRICT

Timestamps are UTC Unix seconds. UUIDv7 values are generated by the application. Enable foreign keys on every connection and use WAL for the single-node deployment.

07

Security & Transaction Rules

Must

Atomic exchange

Use BEGIN IMMEDIATE. Update an active, unexpired token to consumed with a guarded predicate; require exactly one changed row before upserting the account and inserting its session.

Must

Ownership from middleware

Never accept accountId from a user-owned API body. Resolve it from the session and include it in every domain query and unique constraint.

Must

Same-origin deployment

Serve the PWA and API under one origin so the host-only cookie works predictably. Validate Origin on authenticated mutations in addition to SameSite=Lax.

Must

Layered throttling

Suggested defaults: 5 sends/email/15m, 20 sends/IP/15m, 10 exchanges/IP/15m, 60s resend cooldown, and 5 successful deliveries per request.

Operate

Privacy-safe rate keys

Store HMAC-SHA-256(server secret, email_key or IP prefix), not raw addresses. Rotate logs faster than auth records and never log raw bearer tokens.

Operate

Bounded cleanup

Delete expired login requests and tokens after 30 days, expired rate buckets after 24 hours, and revoked session rows after 90 days unless audit policy requires longer. Never delete an active session because of inactivity.

Session rotation detail

Rotate the session secret every 30 active days. Keep the previous digest valid for two minutes so concurrent mobile requests do not fail, then clear it. Reissue the persistent cookie and update last_seen_at at most once per day.

Accepted consequence: without a server TTL, a stolen session remains valid until sign-out or token rotation invalidates that exact copy. Browser cookie caps and site-data eviction can still sign a user out locally, so “until sign-out” cannot be guaranteed against browser or OS cleanup.
08

Failure Semantics

Errors are designed around recovery actions, not provider internals. Every error body uses a stable machine code, user-readable message, and retryable boolean.

Condition HTTP / code Client behavior Data effect
Malformed email 422 invalid_email Keep input; show inline correction. No request row.
Provider unavailable 503 email_delivery_unavailable Show error and Resend immediately. Request retained; token marked failed.
Resend too soon 429 resend_too_soon Disable until Retry-After. No new token.
Link already consumed 409 magic_link_used Offer “Send a new link.” No session created.
Link expired/superseded 410 magic_link_expired Offer “Send a new link.” No session created.
Cookie missing, cleared, or revoked 401 session_required Clear local auth state; preserve offline log queue; re-authenticate before sync. No automatic session expiry; domain records unchanged.

10

Decision Record

Recorded from review

No server-side session expiry

The implementation will follow PRD 24 literally at the server: inactivity does not invalidate a session. Only local sign-out or explicit administrative action revokes the row.

Server behavior

No idle or absolute TTL column. Active rows are never removed by cleanup.

Platform limit

A browser or OS may still cap cookies or clear local site data.

Rotation

Rotate every 30 active days with a two-minute concurrent-request grace window.

Accepted risk

An inactive stolen cookie has no time-based server revocation.

Explicitly excluded

  • Passwords and password recovery
  • OAuth or social sign-in
  • Remote device/session management
  • Sign out all devices
  • Email address change
  • Self-service account deletion
