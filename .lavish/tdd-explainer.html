01

Reading lens

Three kinds of statement live together

The document is easiest to understand when every statement is sorted into one of three buckets. Requirements constrain all future designs; approved design is ready to implement; open decisions still need an owner and a choice.

Required behavior

MUST

Product truths such as account isolation, immutable calendar-date ownership, no plate double counting, and unknown nutrients not becoming zero.

§4 · §7–§15

Approved design

READY

The version-one authentication boundary: same-origin JSON API, five routes, magic-link semantics, secure cookies, five SQLite tables, hashing, rate limits, and rotation behavior.

§6

Open design

DECIDE

Frameworks, providers, domain storage, synchronization protocol, time and unit precision, image handling, observability, and quality gates are deliberately unselected.

The main interpretation: this TDD is strong on behavioral boundaries and authentication, but it is not sufficient by itself to begin the whole application. The unresolved choices in sections 16 and 17 are part of the design, not omissions to ignore.
02

System shape

One approved island inside a larger pending system

The intended product is a mobile-first PWA, primarily for iPhone. Only the authentication boundary and its SQLite model are approved. The dotted branches below describe required capabilities whose technologies are still undecided.

Known now
  • Same-origin PWA and API assumption for authentication
  • JSON bodies and /v1 routes
  • SQLite 3.37+ and UUIDv7 auth identifiers
  • Opaque, hashed magic-link and session secrets
Not known yet
  • Ionic versus another client framework
  • Backend language, hosting, and deployment model
  • Domain database and synchronization design
  • Email, catalog, OCR, and image-storage providers
03

Domain model

The account is the privacy and ownership root

Snapshot semantics

Logged food is copied data, not a live reference to a catalog or favorite. Editing one occurrence cannot mutate the source or a different day.

Derived semantics

Plate nutrition is calculated from its current food components. The plate has no second independent nutrition total to drift out of sync.

Historical semantics

Goals are versioned by effective date, so viewing an old day compares it with the goal that was active then, not today's goal.

04

Non-negotiables

Sixteen invariants protect meaning over time

These rules should become database constraints, transactional checks, authorization policies, and tests. A framework choice is valid only if it can enforce them.

01–02

Ownership

Every private record has exactly one account owner. Cross-account reads and writes must be impossible, including images.

03–06

Calendar time

A food or water event owns one immutable calendar date. Today uses local time; retroactive items append by time; later timezone changes cannot move history.

07–12

Plate integrity

Components are successful, same-day foods; one food cannot be both standalone and grouped. Plate time freezes at creation, totals are derived, and zero components deletes the plate.

13–14

Nutrition truth

Failed records add nothing. A missing nutrient remains unknown, never zero, and can make a daily aggregate explicitly incomplete.

15

Edit isolation

Editing a logged item changes only that occurrence, not provider catalog data, favorites, templates, or another logged occurrence.

16

Image attachment

A successful scan's image cannot be removed independently. Deleting its owning record controls the asset lifecycle.

Five API operations

Approved
Method Route Responsibility
POST /v1/auth/magic-links Request initial email
POST …/{requestId}/resend Retry delivery safely
POST /v1/auth/sessions Exchange link for session
GET /v1/auth/session Restore and refresh session
DELETE /v1/auth/session Sign out this phone only

Five SQLite tables

Approved
Table One row means
accounts One verified identity and ownership root
auth_login_requests One “email me a link” UI attempt
auth_magic_link_tokens One initial or resend secret and delivery outcome
auth_sessions One signed-in phone or browser
auth_rate_limit_buckets One privacy-preserving action/key/time window

Why URL fragments?

#token=… is not sent in the normal HTTP request, reducing exposure to server logs and ordinary HTTP-only link scanners.

Why request rows?

They group initial delivery and resends before an account exists. A failed resend can be recorded without invalidating the prior working token.

Why prior token grace?

Session secrets rotate every 30 active days, but the previous hash remains valid for two minutes so concurrent mobile requests do not fail mid-rotation.

08

Plate semantics

A plate is ownership, not a visual folder

Grouping changes where food records live. The selected entries stop being standalone cards and become owned components, which is why creation and deletion need transactional boundaries.

Operation Allowed input Time behavior Ownership / deletion result
Create plate Named, same-day, successful standalone foods Copies latest selected component time Plate now owns selected food rows
Add new food Create through any ingestion path inside plate Plate time does not change New entry is born as a component
Move existing food Not allowed Not applicable Existing standalone cannot move into existing plate
Remove component Any current component Plate time remains fixed One component is valid; zero deletes plate
Delete plate Logged plate Not applicable Cascades to component foods and attached images
Still unresolved: creation currently says two or more foods, but the document explicitly asks product to confirm that initial minimum. An existing plate with one component is definitely valid.
09

Offline + time

Preserve user intent before trying to reconcile it

Offline conflict policy

Behavior fixed

If two device versions cannot merge safely, preserve both as separate records and let the user delete the unwanted duplicate. Silent loss is worse than a visible duplicate.

Phone A · offline

Entry edited

+

Phone B · offline

Same entry edited

Sync result: preserve two distinguishable records, not “last write wins.”

Three cases sync must distinguish

Protocol open
  1. 01 Intentional duplicate consumption
  2. 02 Conflict-preserving duplicate
  3. 03 Retry of the same pending scan

Local IDs, server IDs, operation logs, idempotency, merge detection, ordering, and retries still need concrete definitions.

Today

Use current local time

The display time reflects when the user logs the item today.

Past date

Append predictably

Use one minute after the newest time, or 12:00 PM if no entries exist.

Timezone change

Keep date stable

Calendar ownership is separate from mutable device timezone behavior.

Important gap: the behavior is clear, but canonical date/time storage, daylight-saving handling, same-minute ordering, normalized units, precision, and rounding are not yet defined.

10

Quality boundary

The tests are a behavioral acceptance suite

The TDD names sixteen minimum testing boundaries without choosing a test framework. Together they define the failure modes implementation cannot regress.

Identity

Links and sessions

Delivery, resend, expiry, replay, idempotency, multiple phones, local sign-out, persistence, and rotation grace.

Isolation

Privacy boundaries

Cross-account data isolation and private image access need direct negative tests, not just happy-path authorization.

Domain

Food, plates, totals

Every lifecycle state, plate operation, no double counting, unknown nutrient propagation, and historical goal selection.

Resilience

Offline and conversion

Restart recovery, later sync, conflict duplication, date stability, unit conversion, water equivalence, and asset lifecycle.

The required cases are listed, but test tooling, coverage expectations, CI gates, performance targets, and reliability targets remain open.
11

Decision frontier

What can be built now, and what blocks the rest

Authentication has a concrete contract. Every other stream has enough behavioral guidance to evaluate options, but not enough selected architecture to implement end-to-end without making new decisions.

Area Status What the TDD gives us Next design obligation
Authentication Approved Endpoints, schema, link policy, sessions, throttles Select backend runtime and email provider; implement contract
Client Open Mobile-first PWA, iPhone priority, required screens/states Choose Ionic or alternative, browser targets, app-store scope
Domain persistence Open Entities, ownership, invariants, transaction needs Choose primary DB, schema, migration and aggregate strategy
Food and scanning Open Catalog, barcode, OCR lifecycle and partial-data rules Select providers, confidence thresholds, fallback behavior
Images Open Private ownership, offline durability, linked deletion Select storage, upload, compression, limits, cleanup
Synchronization Open Offline edits and preserve-both conflict outcome Define operation log, IDs, idempotency, merge and ordering
Time and units Open Stable calendar dates, US/metric display, fixed water presets Define canonical storage, timezone/DST, precision, rounding
Operations and quality Open Security requirements and minimum behavioral tests Choose observability, CI, test stack, SLOs, backup and recovery

Can start

Auth implementation

The API and storage behavior are detailed enough to build once the backend runtime and provider are chosen.

Can prototype

Core product UX

The home, food-log, ingestion, plate, water, pending, and error behavior can be prototyped against the invariant set.

Must decide

End-to-end architecture

Domain data, sync, providers, images, units, time, and operations need explicit technical designs before production implementation.

Bottom line

The TDD protects correctness before selecting machinery.

Its strongest contribution is the invariant set: ownership, historical stability, snapshot isolation, plate integrity, unknown nutrient propagation, durable offline capture, and preservation of conflicting user intent. Authentication then demonstrates the level of specificity the remaining architecture sections still need.

A useful implementation test

For every proposed technology, ask: can it enforce the invariants, survive offline use, preserve privacy across accounts and devices, and prove those properties through the §15 test boundary?
